## 4. 真實端點 E2E 測試結果（68 項檢查）

### 4.1 通過項（67/68）

**管理端與租戶生命週期**
- admin 無 token／錯誤 token → 401；admin 路徑在 public 路由器上 → 404（埠隔離生效）
- 建立 App A / B → 200，回傳 app_key + 32+ 字元 app_secret

**上傳 / 下載 / 令牌**
- 簽名上傳 → 200，回傳 `file_id` + 與本地計算的 `sha256` 完全一致
- embed 連結生成 → 200；**冪等**：同一 (file, user, scope) 在 TTL 視窗內回傳**同一 token**、`reused=true` 且不續期
- 下載 → 200 + 位元組級一致；ETag 存在；`If-None-Match` → 304
- Range：`bytes=2-5` → 206 且切片正確；越界 `bytes=99999-` → 416
- 撤銷 token → 200 且 `revoked=true`；撤銷後下載 → 404；再次 generate → 鑄造**新** token

**跨租戶隔離**
- 租戶 B 對 A 的檔案 generate link／讀 meta → 404（存在性隱藏）；B 的檔案列表為空
- 撤銷與檔案刪除後 token 立即失效

**鑑權加固**
- 偽造 HMAC → 401；**nonce 重放 → 401**（首次 200／重放 401）；過期時間戳 → 401
- 使用者 JWT：正確 → 200；錯誤 secret → 401；未註冊使用者 → 401（fail-closed）

**ACL / 資料夾**
- 目錄建立、上傳到目錄、目錄 ACL 授權、**資料夾級 deny 生效**（繼承 deny → 403）、批次 ACL（updated=2）

**配額與限制**
- 配額：前兩個 10B 上傳 200，第 3 個 90B 上傳 → **429 `quota_exceeded`**，usage 精確為 20B
- 載荷限制：10B > 5B 上限 → **413**；usage/audit 端點正常

**分享令牌**
- share token 綁定 `allowed_ip`：允許 IP → 200，其他 IP → 404

**導出與管理操作**
- 全量導出 → job `ready` → 下載為合法 tar（含 `ustar` magic）
- secret 輪換：舊 secret → 401，新 secret → 200
- admin 軟刪除 App → 204，被刪 App 的請求 → 401
- 刪除檔案 → 204，token 同步失效 → 404，usage 回退

### 4.2 未通過項（1/68）—— 暴露真實缺陷

```
[FAIL] u2 read after batch grant (deny still present)  got 200
```

即：**資料夾上對 u2 的 deny 已經生效（此前 u2 已被 403），但隨後透過檔案級批次 ACL 給該檔案顯式授予 u2 read 後，u2 又能讀了**。詳見 §5.1（高危項）。

**✅ 修復狀態**：`effective_acl` 已改為 deny 獨立全鏈收集，本項在修復後迴歸中變為 PASS（新增整合測試 `inherited_folder_deny_beats_file_explicit_acl` 固化該場景）。

## 5. 發現的問題與風險

### 5.1 🔴 高危：資料夾鏈 deny 可被檔案級顯式 ACL 繞過

**位置**: `src/authz.rs::effective_acl()`

**現象（實測復現）**
1. 資料夾 `invoices` 上設 `deny: ["u2"]` → u2 存取其中檔案回傳 403（deny 生效 ✅）
2. 對該檔案執行批次 ACL 授予 `read: ["u2"]` → **u2 恢復讀取，回傳 200** ❌
3. 資料庫核對：`folders.acl = {..., "deny":["u2"]}` 仍在，`files.acl = {..., "read":["u2"]}` —— deny 未被刪除，只是**不再被檢查**

**根因**: `effective_acl()` 中，祖先資料夾的 deny 收集只發生在「檔案無顯式 ACL」的分支（`else`）；一旦檔案自身有任意 allow 規則（`file_explicit = true`），程式碼直接採用檔案自身規則、**跳過整條資料夾鏈的 deny 收集**。檔案註解聲稱 "but never an inherited deny"，但實作沒有做到。

**與規範衝突**: 專案定稿 `API 規範 (定稿).md` 明確要求「**`deny` 全鏈最優先，檔案蓋不掉繼承的 deny**」「deny 優先於一切 allow」。本缺陷直接違背該安全承諾——合規場景（如在涉密資料夾中拉黑某使用者）可被檔案 owner／批次 ACL 靜默繞過。

**修復建議**: 無論檔案是否顯式，都獨立遍歷祖先鏈收集 `deny`（與 allow 的繼承邏輯解耦），最後 `allow_base.deny = denies`。同時補充整合測試：資料夾 deny + 檔案顯式 allow 的交叉場景。

**✅ 已修復（2026-10-27）**: `effective_acl()` 重寫為兩階段——allow 規則依「檔案顯式或向上繼承」確定；deny 則**無條件**遍歷整條祖先鏈合併（與 allow 解耦、帶 100 層迴圈保護），檔案顯式 allow 無法再蓋掉繼承 deny。新增整合測試 `inherited_folder_deny_beats_file_explicit_acl`（資料夾 deny + 批次 ACL 顯式授權 → 仍 403，owner 不受影響），E2E 中該場景同步改為迴歸斷言並通過。

### 5.2 🟠 中危：IP 綁定的分享令牌可被 `X-Forwarded-For` 偽造繞過

**位置**: `src/routes/mod.rs::ReqCtx::client_ip()`、`src/routes/download.rs`

**現象（實測復現）**: share token 綁定 `allowed_ip=203.0.113.45` 後，任意用戶端只要在請求裡帶 `X-Forwarded-For: 203.0.113.45` 即回傳 200——即使它真實 IP 完全不同。伺服器的 `client_ip()` 直接信任用戶端自帶的 `X-Forwarded-For` 頭，且**沒有任何受信代理組態**；public 監聽還預設綁定 `0.0.0.0`（直連暴露）。

**影響**: IP 綁定形同虛設，分享令牌的可追蹤性／存取控制降級為純令牌隨機性。若產品把 `allowed_ip` 當作安全邊界，這是繞過點。

**修復建議**: 預設使用 TCP 連線的 peer IP（socket 對端）；僅在顯式組態了受信反向代理（且會覆寫 XFF）時才解析該頭；或提供 `TRUSTED_PROXIES` 組態項。

**✅ 已修復（2026-10-27）**: 新增 `Config::trust_xff`（環境變數 `TENANT_FS_TRUST_XFF`，預設 `false`）。預設模式 `client_ip()` 回傳 socket peer IP，`X-Forwarded-For` 被完全忽略；僅當顯式開啟受信代理模式才解析該頭。伺服器改為 `into_make_service_with_connect_info` 注入真實 peer。新增整合測試 `xff_spoof_is_ignored_by_default`（偽造 XFF 不再命中 IP 綁定 → 404）與 `share_token_with_ip_binding`（受信模式仍正常運作）；E2E 新增「真實 peer IP 生效」「XFF 無法改 IP」斷言。

### 5.3 🟠 中低危：未簽名上傳全量落盤後才拒絕；中斷上傳遺留暫存檔

**位置**: `src/routes/app.rs::upload()`

- 上傳在**串流接收完整 body** 後才驗證 HMAC 簽名（為計算 body hash 所必需，設計使然）；但「app_key 已知即可觸發」意味著**知道 app_key（請求頭中的識別符，非機密）的攻擊者可反覆發起無簽名上傳，讓伺服器每個請求先寫滿 max_payload 位元組到暫存檔再拒絕**——CPU／磁碟 I/O 的放大面。
- 用戶端中途斷連時，`blobs/tmp_{uuid}` 暫存檔沒有清理邏輯（本次測試中探測請求正常收尾，未留下殘留；但異常中斷路徑必然遺留）。
- 修復建議：① 啟動時／背景任務清掃 `tmp_*`；② 缺失簽名頭的請求在串流開始前就拒絕（不必等流完）；③ 對 public 端點加簡單限流。

**✅ 已修復（2026-10-27）**: ① 上傳入口新增「缺失 `x-app-signature`/`x-timestamp`/`x-nonce` 即提前 401」預檢查——不再先落盤；② `TempBlobGuard`（RAII）接管暫存檔生命週期，任何錯誤路徑（含流中斷）都會清理；③ `build_app` 啟動時呼叫 `storage::cleanup_stale_tmp` 清掃殘留 `tmp_*`。新增單元測試 `cleanup_stale_tmp_removes_leftovers_only` 與整合測試 `missing_signature_headers_rejected_before_streaming`；E2E 探測更新為「拒絕發生在串流之前」。

### 5.4 🟡 低危（維運）：nonce 與審計日誌無限增長

- `nonces` 表：每次簽名請求插入 1 行（**連簽名校驗失敗的請求也燒掉一個 nonce**）。本報告一輪 E2E（約 40 個簽名請求）後已累積 28 行；無任何清理任務，長期執行表會持續膨脹，拖慢所有寫路徑。
- `audit_log` 無保留／輪轉策略。
- 修復建議：週期任務刪除 `created_at < now - 600` 的 nonce；審計日誌依天／容量輪轉或歸檔。

**✅ 已修復（2026-10-27)**: 新增 `db::prune_nonces`（nonce 保留 ≥1h）與 `db::prune_audit`（保留期預設 30 天，可用 `TENANT_FS_AUDIT_RETENTION_DAYS` 組態），main 啟動背景任務每 10 分鐘清理一次。新增單元測試 `prune_deletes_only_old_rows`。

### 5.5 🟡 低危（效能）：下載時依 uuid 遞迴掃描整個 blob 目錄

**位置**: `src/storage.rs::find_uuid()`（深度 ≤ 5，每次下載全目錄遍歷）

- blob 落盤路徑為 `app_{id}/yyyy/mm/{uuid}`，但 DB 只存 `storage_uuid`，不存 `yyyy/mm` 分片，因此每次下載都要在 app 目錄裡**遞迴查找 uuid**。檔案數多了以後，每次下載都是 O(目錄規模) 的掃描。
- 修復建議：DB 增加 `blob_path` 列（或解析時把 uuid → 直接路徑對映快取）；同時可給每個下載請求保留 canonicalize 校驗防逃逸。

**✅ 已修復（2026-10-27)**: `files` 表新增 `blob_path` 列（migration 冪等加列），上傳時寫入 `yyyy/mm/{uuid}`；`resolve_blob`/`remove_blob` 接受直接路徑，下載／刪除／導出／遞迴刪除均為 O(1) 直查，`find_uuid` 僅作舊資料兜底。`canonicalize + starts_with(app_root)` 逃逸防護對直查路徑同樣生效（新增單元測試覆蓋直查路徑含 `..` 被拒）。

### 5.6 🟡 低危（組態）：server_secret 存在開發預設值

- `config.rs` 預設 `server_secret = "dev-server-secret-change-me"`，若部署時忘記組態環境變數，所有 app_secret 的 AES-256-GCM 加密都退化為公開金鑰可解。
- 建議：偵測到預設值在非開發環境啟動時打顯著警告（或直接拒絕啟動）。

**✅ 已修復（2026-10-27)**: 提取常數 `DEFAULT_SERVER_SECRET` 並在 `main` 啟動時偵測——若命中預設值印出顯著 WARNING（提示 app secret 以該值加密，勿上線）。實測啟動日誌輸出確認生效。

### 5.7 🟢 低危（程式碼品質）：clippy 10 條警告

`redundant closure`×3、`clamp-like pattern`×2、`too many arguments`（`verify_app_signature` 11 個參數，建議封裝為請求上下文結構體）、`equality checks against false` 等。5 條可自動修復。

**✅ 已修復（2026-10-27)**: clippy `--all-targets` **0 警告**。具體：`verify_app_signature` 封裝 `SignatureParts`（11→7 參數）、`db::audit` 封裝 `AuditEntry`（8→3）、`admin::app_json` 改為接收 `&AppRow`、手寫 clamp 改 `.clamp(60, 86400)`、`== false` 改 `!`、redundant closure/`needless_borrows` 全部清理。

### 5.8 🟢 低危（規範偏差）：embed token 依檔案 owner 而非請求使用者鍵控

`generate_link` 傳給 `generate_embed` 的 user_id 是 `file.owner` 而非目前請求使用者——兩名不同的讀者對同一檔案生成 embed 會拿到**同一個 token**（規範描述的是依 (file, user, scope) 鍵控）。實際危害低（有讀權限者本就可生成 share 連結），但與規範表述不一致。

**✅ 已修復（2026-10-27)**: `generate_link` 的 embed 分支改為依請求使用者鍵控（`Identity::User` 用 `user_id`；App 級身分無使用者上下文時回退 `file.owner`），兩名讀者的 embed 令牌不再互相碰撞，與 (file, user, scope) 規範一致。

### 5.9 🟢 觀察項：原始檔名 / Content-Type 不保留

上傳強制 `application/octet-stream`、`logical_path = uuid`，下載檔名也是 `storage_uuid`。若產品需要保留原始檔名／媒體類型，需擴充 API（目前定稿規範如此設計，非缺陷，僅提示）。**保留不修改**（改 API 契約需產品層決策，可在下版 API 增加選用 `filename`/`content_type` 中繼資料）。

## 7. 優點與確認項

- **安全設計完整**：HMAC-SHA256 + ±300s 時間窗 + 單次 nonce 防重放（實測有效）；常數時間比較（subtle crate）；JWT 僅認 app secret 簽名 + 已註冊使用者（fail-closed）；能力令牌 TTL／即時撤銷／冪等視窗；ACL deny-by-default；canonicalize + `starts_with` 路徑逃逸防護（單元測試覆蓋 `..`、跨目錄、符號連結場景）；管理 API 僅綁定 localhost。
- **修復後新增防護**：deny 全鏈最優先（檔案顯式 ACL 蓋不掉繼承 deny）；預設 peer IP 模式（XFF 需顯式受信代理才解析）；無簽名上傳串流前拒絕 + RAII 暫存檔清理 + 啟動清掃；nonce/審計背景定期清理；blob 直查路徑。
- **跨租戶隔離實測通過**：他人檔案一律 404 隱藏存在性，列表依租戶隔離。
- **持久化**：重啟程序後 token 與檔案仍可用（整合測試覆蓋），SQLite WAL + FK。
- **儲存佈局**：`blobs/app_{id}/yyyy/mm/{uuid}`，無副檔名、目錄有界、導出為合法 tar。
- **錯誤模型統一**：`{error:{code,message,request_id}}`，狀態碼語意化（404 隱藏、429 配額、413 載荷）。
- **測試覆蓋**：修復後 36 項（17 單元 + 19 整合）全綠，clippy 0 警告；E2E 69/69 全綠。

## 8. 重現方式

```bash
# 1) 建置
```
