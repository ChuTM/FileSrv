# 多租戶／多 App 隔離的 SaaS／PaaS 級檔案儲存服務 — 完整規劃

> 版本：v1.0　類型：伺服器建置計畫
> 技術棧：Rust（Axum）＋ Redis ＋ PostgreSQL ＋ 內容定址備份（restic）
> 核心目標：**嚴格的數據與存取隔離**，支援多使用者（Users）、多應用（Apps）與租戶分割（Tenant Partitioning）。

---

## 1. 概述與目標

本服務是一個多租戶、多 App 的 SaaS／PaaS 檔案儲存服務，供多個應用（App）後端以 API 方式上傳、存儲、取用檔案。一切設計圍繞「**隔離**」展開，隔離保證**靠結構與密碼學、不靠信任**：

- App 與 App 之間：資料、Redis key、物理目錄、配額、限流全部隔離。
- 使用者與使用者之間：檔案歸屬、ACL 規則、委派身份隔離。
- 伺服器是唯一權威：App 只能「請求」，伺服器才「授權／鑄幣」，deny-by-default。

本服務是一般檔案系統，可存放任意類型檔案（可能很敏感），因此合規、備份安全、鑑權覆蓋全部端點。

---

## 2. 核心設計原則

1. **Deny-by-default，fail-closed**：身份不符、規則缺失、動作未列、DB／Redis 故障，一律拒絕。
2. **伺服器是唯一權威**：存取憑證（capability token）由伺服器自己鑄造，App 只能請求、不能自行頒發。
3. **隔離靠範圍捆綁，不靠偵測說謊**：App 的簽名金鑰只能對自己的 `app_id` 簽名，謊言的作用範圍被鎖在自身命名空間內。
4. **鑑權與規則覆蓋每一支 API**：上傳／列舉／meta／刪除／導出／下載全走同一層統一閘道，且規則分動作。
5. **Token 生命週期與檔案生命週期徹底解耦**：Token 過期只清 Redis key；實體刪除只由明確刪除請求或保留政策觸發。
6. **一切皆有界**：Token 冪等＋固定 TTL、配額原子、記憶體有界、備份可驗證、審計可追溯。

## 3. 總體架構

```
[ App A 後端 ] ──(App A Key + HMAC)──┐
                                      ▼
[ App B 後端 ] ──(App B Key + HMAC)──┼──► [ 多租戶 API 閘道 (Rust / Axum) ]
                                      │      ├─ ① 鑑權：App HMAC / user JWT / token / admin
                                      │      ├─ ② 規則：deny-by-default，分動作 (read/write/delete/list/export)
                                      │      ├─ ③ 資源範圍：WHERE app_id = 身份.app_id（雙保險）
                                      │      └─ ④ 判決：允許→執行＋計數｜拒絕→403/404，全寫審計
                                      └──────────────┬──────────────┐
                                                     ▼              ▼
                              [ Redis 狀態層（命名空間隔離）]   [ 物理檔案層（App 目錄隔離）]
                              app:{id}:…:token / usage      /storage/blobs/app_{id}/yyyy/mm/uuid
                              （含 quota、rate-limit）       （無副檔名、Web Root 外）

                                    ▲              ▲
                              [ PostgreSQL（權威層）]   [ 備份（restic，離站＋不可變）]
                              apps / files / acl       blobs + DB + 金鑰階層
```

## 4. 多租戶數據模型

### 4.1 實體關係（ER）

採用三層模型：**Account（帳戶／租戶持有者）— App（應用）— User（App 內終端使用者）**，外加 **Folder（資料夾）**。

```
Account 1 ── 擁有 ── * App        # 帳戶擁有多個 App；建 App 的是 Account／運營者
App     1 ── 包含 ── * User      # 終端使用者住在 App 內；user_id 為 App 內作用域 (app_id, user_id)
App     1 ── 擁有 ── * Folder    # 資料夾樹：parent_id 指向父資料夾；根資料夾 parent_id NULL
Folder  1 ── 包含 ── * File      # 檔案可掛在資料夾下（files.folder_id）
App     1 ── 擁有 ── * File
User    1 ── 擁有 ── * File      # File 歸屬於特定 app_id 與 user_id，另存 ACL
```

- **Account（帳戶／租戶持有者）**：SaaS 客戶／運營者，擁有一個或多個 App。DB 一等實體。
- **App（應用）**：屬於一個 Account；每個 App 有獨立的 `app_key`、`app_secret`、獨立配額（quota）與檔案空間。DB 一等實體。
- **User（App 內終端使用者）**：屬於唯一一個 App；**`user_id` 是 App 指定的不透明識別符（不是顯示名），App 內不得重複**。身分一律 `(app_id, user_id)` 複合。使用者目錄由 App 自行管理（App 是身份權威，用 user-context JWT 替用戶簽身份）；本服務以 `app_users` 表強制唯一性，不維護全域 user 表。
- **Folder（資料夾）**：屬於一個 App，形成資料夾樹；每個資料夾有自己可選的 ACL，供其下檔案繼承。
- **File（檔案）**：歸屬於特定 `app_id` 與 `user_id`，可掛在資料夾下，另存 ACL。

### 4.2 Redis Key 命名空間隔離

所有 Key 必須帶 App／User 前綴，防止跨 App 洩漏：

```
app:{app_id}:usage:bytes                             # 該 App 已用儲存空間（原子計數）
app:{app_id}:embed:{file_id}:{user_id}:{scope}       # embed 冪等主鍵 → 當前 token
tok:{token}                                          # 反向索引 → embed key（revoke 定位用）
```

### 4.3 PostgreSQL Schema（權威層）

```sql
apps(
  id BIGSERIAL PK, name TEXT, app_key TEXT UNIQUE, secret_hash TEXT,
  quota_bytes BIGINT, max_payload_bytes BIGINT,
  enabled BOOL, created_at, deleted_at            -- deleted_at 非空＝軟刪除
)

app_users(
  app_id FK, user_id TEXT,                        -- user_id 為 App 指定、不透明
  PRIMARY KEY(app_id, user_id),                   -- App 內唯一（不得重複）
  created_at
)

folders(
  id BIGSERIAL PK, app_id FK, parent_id FK NULL,  -- 根資料夾 parent_id NULL
  name TEXT, acl JSONB, classification TEXT,
  created_at, deleted_at
)

files(
  id BIGSERIAL PK, app_id FK, user_id TEXT,       -- user_id 對應 app_users
  folder_id FK NULL,                              -- 檔案所屬資料夾
  storage_uuid UUID, logical_path TEXT, content_type TEXT,
  size BIGINT, sha256 TEXT, classification TEXT,  -- public/internal/confidential/restricted
  owner TEXT, acl JSONB,                          -- {read,write,delete,list,export,deny,public_read}
  created_at, deleted_at
)

audit_log(id, actor, action, app_id, target, ip, decision, at)  -- append-only，見 §12.6
```

`app_secret` 只存 **hash（HMAC-keyed 或 argon2）**，不存明文；建立時明文只回一次。

## 5. 物理儲存隔離

### 5.1 目錄佈局

```
/var/app/storage/blobs/
├── app_01j8x2a9/            # App A 專用目錄
│   └── 2026/10/
│       ├── 9b1deb4d-…       # 無副檔名 UUID 檔案
│       └── f47ac10b-…
└── app_08m9k3z4/            # App B 專用目錄
    └── 2026/10/
        └── a1b2c3d4-…
```

- 所有檔案無 `.php` 等副檔名，存放於 Web Root 之外。
- 按 `app_id / 年月 / uuid` 分層，避免單一目錄過多檔案。

### 5.2 路徑安全

`starts_with` 字面檢查可被 `..` 繞過，**必須先歸一化再驗證**：

```rust
async fn resolve_within_app(root: &Path, app_id: &str, uuid: &str) -> Result<PathBuf> {
    let app_root = root.join(format!("app_{app_id}")).canonicalize()?;
    let candidate = app_root.join(uuid).canonicalize()?;
    if candidate.starts_with(&app_root) { Ok(candidate) } else { Err(/* 越界 */) }
}
```

並在寫入時拒絕 symlink／hardlink 逃逸。

## 6. 鑑權與授權

### 6.1 四種身份來源

| 端點 | 鑑權方式 | 身份 |
|---|---|---|
| 上傳／列舉／meta／刪除（使用者級） | user-context JWT（App 委派簽署） | `(app, user)` |
| 導出（App 級）／App 管理 | `X-App-Key` + HMAC 簽名 | `app` |
| 下載（`/download/:token`） | 伺服器鑄幣的能力 token | `token`（綁 file+user+TTL） |
| 內部管理（localhost） | `Bearer <ADMIN_TOKEN>` | `admin` |

### 6.2 統一鑑權＋規則閘道（覆蓋每一支 API）

```
端點 → ① 鑑權（身份來源）→ ② 規則引擎 evaluate(subject, resource, action)
      → ③ 資源範圍（WHERE app_id = 身份.app_id）→ ④ 判決＋計數＋審計
```

鑑權／規則為第一天就內建的控制；對抗性安全測試放在建置尾聲執行。

### 6.3 分動作規則引擎（FileAcl）

```rust
enum Action { Read, Write, Delete, List, Export }

struct FileAcl {
    owner:        String,
    read:         Vec<String>,   // 誰能讀（含共享）
    write:        Vec<String>,   // 誰能傳／覆寫
    delete:       Vec<String>,
    list:         Vec<String>,   // 誰能在清單看到
    export:       Vec<String>,   // 誰能包進導出
    deny:         Vec<String>,   // 單點撤回，優先於一切 allow
    public_read:  bool,
}
```

App 可設預設，檔案可覆蓋。求值順序：**① 身份 ② 資源中繼（以 file_id 為準，不解析路徑字串）③ deny 命中→拒絕 ④ owner==subject→允許 ⑤ allow 命中（user_id／group／"*"）→允許 ⑥ 否則拒絕**。任何異常→拒絕。

**ACL 可變性**：`allow/deny` 只有 owner（或具 owner 權限的 App 管理員）能改，否則任何使用者都能替自己授權（權限提升）。

### 6.4 user-context JWT（委派身份）

App 後端替最終使用者簽短效 JWT（內含 `user_id`），閘道驗籤後把 `user_id` 寫入請求 context；**請求體／header 自帶的 `user_id` 一律忽略並覆蓋**——否則任何使用者只要把欄位改成他人 ID 就繞過。

### 6.5 App 層 HMAC 簽名（含重放防護）

簽名須帶 **timestamp + nonce + canonical request**，驗證 constant-time，防止 replay；App Secret 不在網路傳輸，只在客戶端計算簽名。

### 6.6 資料夾、繼承 ACL 與 App 層權限管理

**資料夾（Folder）**：屬於一個 App，形成資料夾樹；`files.folder_id` 把檔案掛到資料夾下。資料夾與檔案各有可選 ACL。

**權限解析（繼承）**——找最近的顯式 ACL：

```
effective(resource) = resource.acl 若有
                      → 否則其父資料夾 acl → 祖先… → 否則 app 預設
```

- **`deny` 全鏈最優先**：任一層 deny 命中即拒絕，檔案蓋不掉繼承的 deny。
- **owner 預設可存取**（除非被 deny）。
- 檔案可覆蓋繼承的 allow。

**兩個管理者層級**：

| 管理者 | 身分 | 權限範圍 |
|---|---|---|
| App 層（tenant admin） | `X-App-Key`＋HMAC | 管理該 App 內**任一**檔/資料夾 ACL，含**批量**與資料夾遞迴 |
| User 層（owner） | user JWT | 管理**自己擁有**檔案的 ACL |

**批量權限操作**：
- `PATCH /v1/folders/{id}/acl` — 設資料夾 ACL，可 `recursive:true` 套用到底下所有未覆蓋檔案。
- `POST /v1/files/batch/acl` — `{ file_ids:[…], action:"read", add:[…], remove:[…] }`；有批次上限、冪等、整批單一審計、rate-limit。
- 資料夾 CRUD：`POST/GET/PATCH/DELETE /v1/folders…`。

**App 層批量管理權限範圍仍受 `app_id` 硬綁**：批量操作只作用於已驗證 App 自己的檔案/資料夾，不接受跨 App 目標。

## 7. Token 系統

### 7.1 兩類 Token：share vs embed

| 維度 | share（一次性分享） | embed（內嵌／重複檢視） |
|---|---|---|
| 典型場景 | 分享下載一份檔 | `img src` 載入圖片／重複檢視 |
| IP 綁定 | 是（防轉發） | 否（用 exp；瀏覽器 NAT/CDN 會誤傷） |
| token 生成 | 隨機，每次一個 | 確定性／冪等，同 (file,user,scope) 同一 |
| Redis 記憶體 | 每請求一 key | 有界（每 (file,user) 一組 key，非每請求） |
| 壽命 | 短 TTL，單次 | **固定窗口**：首次起算 30 分鐘，刷新不續命 |
| HTTP 快取 | 不適用 | ETag + `Cache-Control: private`，刷新走 304 |

### 7.2 冪等 + 固定窗口（embed）

```
SET app:{id}:embed:{file_id}:{user_id}:{scope} = <token> EX 1800 NX
```

- 首次 `NX` 成功 → 鑄新 token，TTL=1800 從此刻起算。
- 之後 30 分鐘內任何刷新 → 回傳**同一個** token，**不延長 TTL**。
- 1800 秒後自動過期 → 下次 generate 鑄全新 token（新窗口）。
- 記憶體有界：key 數＝近 30 分鐘內「不同 (file,user,scope)」，不是請求數；由 TTL 自清。

語意：**刷新不續命**。若改成命中即 `EXPIRE`，就變滑動窗口、趨向靜態，與需求衝突。

### 7.3 金鑰佈局＋revoke 生命週期

```
embed:{app}:{file}:{user}:{scope}  = 當前 token      ← 冪等主鍵，固定 TTL
tok:{token}                        = embed key       ← 反向索引，revoke 定位用
```

- **revoke(token)**：Lua 原子 `GET tok` → `DEL tok + DEL embed` → token 即時失效 → 下次 generate 鑄新。
- **verify(token)**：查 `tok`（nil→過期/撤銷）→ 查 embed 是否仍等於該 token（不等→被取代）→ 都過才放行。
- **沒 revoke → generate 一直回傳同一個 token；revoke → 即時失效 → 重鑄。**

### 7.4 Lua 腳本（全原子，一次 round trip）

```lua
-- get_or_create：KEYS[1]=embed key  KEYS[2]=tok:{token}  ARGV={token, context=embed_key, ttl}
local cur = redis.call('GET', KEYS[1])
if cur then return cur end
redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[3])
redis.call('SET', KEYS[2], ARGV[2], 'EX', ARGV[3])
return ARGV[1]
```

```lua
-- revoke：KEYS[1]=tok:{token}
local embed_key = redis.call('GET', KEYS[1])
if not embed_key then return 0 end
redis.call('DEL', KEYS[1])
redis.call('DEL', embed_key)
return 1
```

```lua
-- verify：KEYS[1]=tok:{token}  ARGV[1]=token
local embed_key = redis.call('GET', KEYS[1])
if not embed_key then return 0 end
local cur = redis.call('GET', embed_key)
if cur ~= ARGV[1] then return 0 end
return 1
```

Lua 不做密碼學；token 由 Rust 側用 CSPRNG／HMAC 生成後作為 ARGV 傳入。

### 7.5 併發（1000 用戶）

- 不同 (file,user)：彼此獨立，Redis 單執行緒 ~10 萬 ops/s，微不足道。
- 同一個 (file,user)：Lua get_or_create 原子序列化，只有 1 個會鑄造，其餘 999 全拿同一 token，**無重複、無 thundering herd**。
- 用 redis-rs multiplexed 連線／連線池；瓶頸在連線池與網路，不在 CPU。

## 8. 配額與防霸佔（Noisy Neighbor）

- **原子配額（防 TOCTOU 競態）**：配額扣減用 Redis Lua `INCR + cap` 單一腳本。

```redis
-- 原子配額：INCR + cap 同一腳本
local used = redis.call('GET', KEYS[1]) or 0
if used + tonumber(ARGV[1]) > tonumber(ARGV[2]) then return 0 end
return redis.call('INCRBY', KEYS[1], ARGV[1])
```

- **每 App rate limit**：generate／upload／export 等分別限流（例如每秒 100 次 generate）。
- **下載端限流**：download 無 App key，需按 token／client IP 另做限流。
- **單檔上限**：`max_payload_bytes`，邊傳邊卡、不把整檔讀進記憶體。

## 9. 檔案生命週期與一致性

- **Token 與檔案生命週期解耦**：Token 過期只清 Redis key，**絕不觸發刪實體檔**。實體刪除只由「明確刪除 API」或「保留政策」驅動。
- **刪除**：`DELETE /files/{id}` → 綁 app+user 歸屬、軟刪（tombstone）→ 寬限期後實體 rm + 撤銷該檔 token。
- **一致性調和（reconcile）**：
  - DB row ↔ 磁碟 blob 對帳、清孤兒；
  - Redis 用量計數 ↔ 實際磁碟重建；
  - 定時 reconcile job。

## 10. 控制平面（內部管理）

- **網路邊界**：admin 監聽綁 `127.0.0.1`，與對外 app API 是兩套 router、兩個監聽地址。admin 永不接受 `X-App-Key`／HMAC，只用自己的憑證。
- **鑑權**：`Authorization: Bearer <ADMIN_TOKEN>`，token 來自啟動環境變數（高熵），constant-time 驗證，fail-closed；可選 bootstrap token 換短效 admin session。
- **Apps 管理**：create／list／detail／patch（啟用、配額、單檔上限）／**secret rotate**（寬限期）／**soft-delete**（quarantine → tombstone → 寬限期後清 blobs + Redis 命名空間）。
- **備份與審計端點**：`/admin/v1/backups*`、`/admin/v1/audit`。

## 11. 備份與災難復原

- **範圍**：只備兩樣——① blob 目錄樹（不可變 UUID 檔）；② DB dump（權威：apps/files/acl）。**Redis token 不備**（30 分鐘生命週期、可重建）。
- **工具**：restic／borg——內容定址去重、加密、不可變快照、內建完整性。
- **一致性**：blobs 不可變，與 DB 獨立備份不撕裂。
- **排程與保留**：增量每 6h + DB dump；保留 `daily×7 / weekly×4 / monthly×6`；**離站副本**；快照設不可變防勒索。
- **金鑰階層必須一起備**：加密的 blobs 若 KEK/DEK 沒備或 escrow，到時還不了原。金鑰備份與資料備份**分開存放**。
- **完整性**：每檔入庫算 `sha256`，restic `check` 定期驗證。
- **恢復權限**：能 restore＝能看全部資料 → 高鑑權＋審計＋**定期 restore drill（sha256 校驗還原）**。
- **抹除 vs 保留政策**：合規要求「個人資料可應要求抹除」，但不可變備份會保留 → **寫成明訂政策**（例如：抹除請求 → 刪 DB＋實體＋標記，備份按最短保留期滾動、到期即不再留）。

## 12. 安全強化

1. **靜態加密**：信封加密（每檔 DEK，KEK 走 KMS/HSM）、金鑰輪換、App 刪除時金鑰撤銷。
2. **傳輸**：對外 app API 強制 TLS/HTTPS（HSTS、限 cipher）；敏感場景 mTLS。
3. **安全伺服**：`Content-Disposition: attachment`＋`X-Content-Type-Options: nosniff`＋CSP，防 `.html/.svg` 載 script；MIME 不從檔名推（內容嗅探）。
4. **上傳掃描**：任意檔 → AV/malware 掃描（異步、進隔離區）。
5. **資料分類**：`classification: public/internal/confidential/restricted`，加密強度、保留期、是否可導出、審計粒度按類別分級。
6. **審計**：append-only＋雜湊鏈／WORM 防竄改；admin 角色分離（operator vs auditor）+ 2FA；管理員不能默默讀使用者檔案。
7. **資料駐留**：per-tenant 區域固定（資料留在指定 region），blob 與備份地點可向客戶承諾。

## 13. App 自助導出

- **硬範圍**：export 端點只認 App 憑證，硬綁 `app_id`，**不接受目標 app_id 參數**；`WHERE app_id = 已驗證的 app`，deny-by-default。
- **異步 job**：`POST /apps/export` → job → `GET status` → 下載 archive；job 與 archive 有 TTL、到期清理、per-app 併發上限＋rate-limit。
- **產物安全**：UUID→archive 防 **zip-slip**（不把 logical path 原樣寫入）；archive 靜態加密、不留明文暫存；下載連結用能力 token（短 TTL）。
- **審計與授權**：導出＝搬走大量敏感資料，**留痕、可查**，可選需 admin 批准；archive 明確定義生命週期（用完即清）。

## 14. 建置範圍與順序

**將實作的功能模組**：

1. **上傳**：分塊／斷點續傳＋每塊 checksum＋finalize；上傳冪等鍵；邊傳邊卡 size；partial chunk 清理。
2. **檔案 CRUD**：`GET /files/{id}`、`GET /files`（分頁游標）、`DELETE /files/{id}`（歸屬＋軟刪＋rm＋撤 token）。
3. **下載與 Token**：generate（冪等）／download（Range、HEAD、ETag）／revoke。
4. **導出**：異步 job＋硬範圍＋產物安全。
5. **控制平面**：Apps CRUD、secret rotate、soft-delete、usage、備份、審計。
6. **備份與調和**：restic 管線、DB dump、restore drill、reconcile job。
7. **作業／監控**：secrets 佈建、DB migration、健康檢查＋graceful shutdown、metrics＋告警、**Redis/DB down 一律 fail-closed**、下載 per-IP 限流。
8. **對抗性安全測試（尾聲）**：跨租戶讀取、path traversal（`..`／symlink）、token 偽造／重放、改 logical path 繞 ACL、1000 併發 load／soak、ACL 屬性測試、上傳/導出 fuzz。

**建置順序**：先上傳＋檔案 CRUD（第一行程式碼即內建鑑權＋規則閘道）→ 一致性調和 → 作業／監控 → 最後做對抗性安全測試，驗證隔離與閘道無漏洞後才對外開放。
